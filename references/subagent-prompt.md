# 写章节的子 agent prompt 模板

主 agent 写第一章；其余章节一章一个子 agent（分院帽、梯子是一条线或一个出口一个），全部放在同一条消息里发出去（`subagent_type: general-purpose`，后台跑）。

`<尖括号>` 里换成这一章的内容。子 agent 只看得到这段 prompt，衔接信息不写，它就不知道玩家此刻手里有什么。

```
你是《<游戏名>》的编剧（<类型一句话>）。请写第 <N> 章《<章名>》的完整剧本。

先读这四个文件（必读）：
- <游戏目录>/story/SPEC.md：指纹、设定、主角卡、人物表、声音卡和呼称表（每个人照它说话）、已发生事实表、伏笔表、数值规则、本章的弧形和分场表、文件格式、写作要求
- <skill 目录>/references/character-writing.md：怎么把人物写活；演出和声音用量（§4）；弧形、选项和数值口径（§5）
- <游戏目录>/story/registry.js：可用的场景、说话人、表情、表情符号、姿势、配乐、环境音、音效、转场、数值、结局 id
- <游戏目录>/story/ch1.js：第一章，格式示范和语气参考

任务：
- 写 <游戏目录>/story/ch<N>.js。id "ch<N>"，loop <N>，节点前缀 c<N>_，按 SPEC 里本章的弧形和分场表写。
- 开场：<上一章（或分出来之前）最后一幕发生了什么>。<本章开头玩家手里有什么：各数值的范围（solve --vars 实测）、可能拿到的线索、哪些 g_ flag 可能为真，各自代表什么、为假时代表什么，用条件台词分开说>。已经发生的事以 SPEC 的已发生事实表为准。
- 结局：<按 SPEC 本章的结局形状写章末判定：哪些条件进哪个结局或下一章>。写完在游戏目录下跑 `node tools/solve.js --endings`，确认本章的每个出口都走得到。<结局形状是分好坏时加：跑 `node tools/solve.js --odds <章末判定节点>`：本章开头数值最低的玩家全选对要能到好的那个，最高的随机选进好的那个 ≤ 40%>
- 人物：<本章的重点角色：缺、缺陷，选用了的原型 / 反差 / 秘密，这章要揭开或推进什么>；<配角负责什么>；主角<型和靠什么动起来>，<分场表里写的那个只有主角能做的决定>。
- 弧形自己的要点照 character-writing §5.1；解法必须是前文埋过的，不许巧合、外力救场。
- <节点数下限>–<上限> 个节点，至少 <K> 个有意义的选择点，<几> 次限时选择（故事里没有真的时间压力就写 0），<几> 张 CG（<CG id>），<换装要求>，<场景和同屏要求>。每个场景都要有表情变化和一处姿势或动作；表情符号、震屏、配乐、静音的用量照 character-writing §4。
- 写的顺序：先把主路连着写完，再写别的出口和分支，最后对一遍分支汇合处的台词。
- 写完在游戏目录下运行 `node tools/validate.js story/ch<N>.js`，必须 0 错误；提醒也尽量清零。自己量：旁白 ≤ 35%、带「……」的行 ≤ 15%、主角说出口的台词比例照 character-writing §1.3。
- validate 过了以后，再读 <skill 目录>/references/defaults-check.md 对照自查（写之前别读，它会变成灵感）：命中的说得出非要不可的理由，说不出就换。
- 交回前自己改一遍：陈词滥调、多余解释、华丽辞藻、句子太长、空泛、别扭用词、时态混乱，七类各扫一遍；删掉替角色说破情绪的旁白。

约束：
- 只创建/修改 ch<N>.js 这一个文件，不要改其他文件。需要新场景、新音效就在最终回复里提出，不要自己加。
- 不新增、不改写已经发生的事；要引用先查事实表。SPEC 里写死的共用原文一字不差。
- 别的重点角色在本章出场：照 TA 的声音卡说话；不揭 TA 自己的秘密；给 TA 一个交代，不能凭空消失。
- 不去读别的游戏的剧本找灵感；人物、物件、台词都从本作的 SPEC 里长出来。
- 不使用任何图像、视频生成工具。
- 台词像真人，人物声音各不相同，口癖少而准。这是给真实玩家玩的成品，质量要高。

最终回复（简短）：节点数、台词数、选择点数（各类型几个）；数值或条件怎么设计的、相关读数；各出口怎么走到；新埋 / 回收了哪些伏笔；defaults-check 命中了哪几条、为什么留；需要我补什么。

本章铁律（写完对一遍）：
1. 只写 ch<N>.js 这一个文件
2. 每个出口都走得到；<分好坏时：--odds 两条都过>
3. 每个人照声音卡和呼称表说话
4. 解法前文埋过
5. validate 0 错误
```

## 写的时候注意

- 「只写一个文件」最要紧：几个子 agent 并行改同一个文件会互相覆盖
- 本章开头的数值范围必须是实测的（`solve.js --vars`），不要估
- 让子 agent 自己跑 `--endings`（分好坏时加 `--odds`）：它比主 agent 更清楚自己的条件怎么设的
- 铁律放在 prompt 最后：离输出最近的指令最管用
- 后一章依赖前一章的事实：先把前一章的事实写进 SPEC 的已发生事实表再并行；写死不了的就别并行
- 子 agent 写到一半，主 agent 改了前面的事实：马上 发消息告诉它改了什么、哪些 flag 的含义变了
- node 不在系统 PATH 里的机器，在 prompt 里写明 node 的绝对路径
- 最终回复要格式固定、要短：主 agent 要收好几份回报

## 交回后主 agent 做的事

- 全量 validate；`solve.js --endings`：所有结局都能走到
- 跨章核对：SPEC 里写死的共用事实各章是否一字不差；同一件事（时间、地点、谁在场）各章说法是否一致
- 抽读最关键的两段戏
- 把各章要求补的场景、音效统一加进 registry 和美术引擎；新伏笔补进 SPEC 的伏笔表
- 列一张素材使用表：场景、配乐、环境音、CG、表情、姿势各用了几次、在哪几章（`dump_story.js` 的文本；姿势、动作 grep `chN.js` 里的 `pose` `act`）；登记了没用的、某人从头到尾没换过的表情，补戏或删登记
- 派审读 agent（`consistency-review.md`）
