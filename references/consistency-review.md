# 剧情一致性审读

`validate.js` 查得了结构：线索有没有发、发在用之前没有、时间有没有倒退。查不了内容：角色说出了他此刻不该知道的事、人设跑偏、选项答应的事后面没兑现、救场的因果说不通。这一层交给审读 agent。

## 什么时候做

- 各章交回、全量 validate 0 错误之后，开始配音之前：配完音再改台词要重配
- 一章一个审读 agent，全部放在同一条消息里发出去；一章 20–30 个节点约 6–19 万 token、2–12 分钟（实测）
- 审读 agent 不能是写这一章的那个：自己审自己，看不出问题
- 第一章也要审：主 agent 自己写的那一章问题往往最多（实测：几个游戏里主 agent 写的那章「严重」都最多）
- 第一章可以在子 agent 写其余章的同时就审，不用等；审完改了事实，马上告诉还在写的子 agent
- 主 agent 自己补的场景、登记、改动，要在审读之前改完；改在审读之后就再审一遍

## 给审读 agent 的材料

- `story/SPEC.md`：指纹、真相、默认时间轴、人物表、声音卡和呼称表、已发生事实表、伏笔表、本章分场表
- 本章和它前面所有章节的压缩文本：`node tools/dump_story.js ch1 … chN > work/review/dump_chN.txt`
  - 只给本章不够：「前面拿到过什么、谁已经知道了什么」都在前面章节里
- 汇合点表：`node tools/solve.js --merge [chN] > work/review/merge_chN.txt`
  - 每个入度 ≥ 2 的节点，列出各条来路到达时哪些 flag 不同、谁在场、好感范围
  - 「严重」最集中在这（实测）
- 不给原始 JS：压缩文本已经有全部台词、选项、条件；要对原文时让它自己读
- node 不在系统 PATH 里的机器，prompt 里写明 node 的绝对路径，并写「不要自己搜 node」：找不到 node 时 agent 可能递归搜整个磁盘，很慢
- 平行的几条线要对照彼此的世界事实（同一个时间点发生什么），把另一条线的路径也告诉它

## prompt 模板

```
你是互动剧情游戏《<游戏名>》的剧本审读。只读、只报问题，不改任何文件。

先读：
- <游戏目录>/story/SPEC.md
- <项目>/work/review/dump_ch<N>.txt：第 1 到第 <N> 章的压缩剧本（"·" 是旁白；"? 选项" 后面括号里是出现条件和得到的东西；"⇢" 是条件跳转）
- <项目>/work/review/merge_ch<N>.txt：汇合节点各条来路的 flag、在场的人、好感范围
- <skill 目录>/references/character-writing.md 第 5、6 节；<skill 目录>/references/defaults-check.md
- 需要对照原文时读 <游戏目录>/story/ch<N>.js（只读）

审第 <N> 章，逐条查下面这些，每条都要有原文依据：
1. 信息泄露：角色或旁白说出了此刻还不该知道的事。对照这条路径上玩家已经经历的；不在场时说的事、别的路线才有的事都算
2. 事实表、伏笔表：台词和已发生事实表矛盾；回收了没埋过的东西；揭示了某件事却没登记
3. 时间、地点、在场：和时间轴、事实表矛盾；同一时刻一个人在两个地方；不在场的人在说话；节点 time 和剧情里说的时间对不上
4. 声音和称呼：对照声音卡和呼称表。遮住名字读，哪句像别人说的；用了「绝不说」里的词；称呼对不上；口癖超次数；前后自相矛盾
5. 选项和后果：选项文字承诺的动作后面没发生；两个选项走向和回应一样，选择没有意义
6. 设定禁止项：SPEC 写明不许出现的内容
7. 结局条件：branch 和 SPEC 写的对不上；坏结局不是玩家选择的直接后果
8. 选项：明显的讨好 / 找骂选项；加分理由用 TA 的「缺」解释不通；主要互动是分好感时，各类选项超配额
9. 人物写活了没有：带「……」超 15%；同屏各说各的；一大段对话表情不变；反差第一次出场就说完了；配角、别的重点角色凭空消失
10. 站位和在场：stage 上站着的人和此刻在场的人对不上（人走了还站着、没进门就在说话、画外的人没写 off）
11. 姿势和动作：旁白说的动作和立绘的 pose / act 对不上
12. 限时选择：timeout 的内容是不是沉默、犹豫的后果；这里真有时间压力吗
13. 每条路径都走一遍：按 merge 表逐个汇合节点、逐条来路读，台词在每条来路上都说得通；回应选项的条件台词按选项 set 的 f_ 分，还是按好感值分（按好感值分会串）
14. 内容安全，命中一律「严重」：未成年角色有性暗示或身材描写；被拒后继续接触；占有欲换好感；拒绝写成害羞
15. 奇迹转折：高潮、转折的解法第一次出现在哪；新出现的外力、巧合、超自然救场算「严重」；SPEC 选的弧形自己的要点没做到，报「一般」
16. 说明台词：角色把双方都知道的事说给对方听
17. 伏笔和承诺：伏笔表里的东西，看得到它的每条路线都回收了没有；人物表写的变化落地了没有；共用的原文是否一字不差
18. 因果和物理：救场、机关、设定的因果说不通（声音、电、气、时间、距离、谁能知道什么）；数字自相矛盾（年龄、年份、时长）
19. 套路：对照 defaults-check.md，命中且看不出非要不可的理由，报「一般」

不要报：文笔偏好、可以更好但没错的地方、标点。

输出（简短，按严重程度排）：
- 每条一行：[严重|一般] 节点 id：「原文」→ 问题是什么，依据是 SPEC 哪句或哪个节点
- 没找到问题就写「第 <N> 章未发现问题」
- 最后一行：查了 19 类，各几条
```

- 不让审读评文笔：创意写作里 LLM 评审和专家的判断不相关（原文），只查能对着原文核对的
- 第 14 类的依据：平台按画面外观判断年龄（SKILL 红线）
- 第 15 类的依据：读者讨厌没铺垫的「miracle turns」（原文）
- 第 18 类：几次实测里最常见的「严重」之一，作者自己写的时候顺着情绪走，物理和时间算不过来

## 收到结果以后

- 主 agent 逐条核对：审读也会误报，打开原文看一眼再改
- 确认是真问题的，主 agent 直接改 `chN.js`，改完重跑 validate、solve、playtest
- 「严重」的一条都不能留；「一般」的视情况改，不改的在 README 或 LOG 里写一句为什么
- 改了已经发生的事实，同步 SPEC 的已发生事实表；有子 agent 还在写，发消息告诉它
